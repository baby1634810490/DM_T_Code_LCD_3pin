# 统一TSDA硬件变体能力配置

- 状态：已接受
- 日期：2026-08-06

## 背景

3Pin 与 Chassis 使用相同的 TSDA-C12D CAN 协议和速度模式运动逻辑，但硬件能力不同：3Pin 的抱闸由 MCU GPIO 控制、限位来自板级输入；Chassis 的抱闸由驱动器随使能自动联动、限位来自寄存器 `0x58`。如果统一 App 直接判断产品编号，硬件差异会扩散到状态机和 Driver，后续维护容易出现两套流程漂移。

## 决策

使用一份源码和一个编译期宏 `TSDA_HARDWARE_VARIANT`：数值 `3` 构建 3Pin，数值 `4` 构建 Chassis。宏只在 `App_User/tsda_config.h` 中翻译为只读能力配置，包括限位观察策略、抱闸控制所有权、抱闸等待时间和当前阶段是否开放自动寻限。

统一 App 只判断能力策略，不直接判断 3Pin 或 Chassis。Driver 不包含配置文件，不区分硬件变体，继续完整表达 TSDA 协议。CAN1 发送适配器和现有 CAN 接收入口保持不变；板级层只注入 GPIO 回调。

## 后果

同一套 App 和 Driver 可以通过一个宏构建两种硬件。Chassis 已实测的 `0x58` 自动寻限和速度规划路径保持原样；3Pin 可以分阶段接入抱闸、板级限位和后续寻限，而不复制状态机。

代价是每增加一种硬件能力，都必须先把差异表达为明确策略，不能在业务状态中临时添加产品编号条件。每次修改必须同时执行 Profile 3、Profile 4 的编译和关键时序回归。

## 否决方案

- 两套 App/Driver 源码：短期改动直接，但相同协议和运动逻辑会持续分叉。
- App 内到处使用产品编号条件编译：实现快，但产品身份侵入统一状态机。
- 运行时可修改 Profile：存在运行中误切换抱闸和限位策略的安全风险，不采用。
